**RED-phase findings from review (fix round 1)**
- **Important 1 — the `try` also wrapped the replication branch, creating a hot spin loop.** A `ValueError`/`KeyError`/`JSONDecodeError` inside `_replication()` (reachable via a truncated `manifest.json` — the disk-full case the breaker exists for) fires before `pending_replications.pop(0)` and before `proposal_attempts += 1`. Classified as an ordinary proposal error, the pass reset the breaker and `continue`d with **nothing advanced**, so the identical failing pass repeated at full speed, writing to `iterations.jsonl` every turn until `max_wall_clock`. The old code `break`ed, so T1 had turned a clean death into an unbounded busy-loop. Confirmed empirically before fixing — the new regression test ran the unfixed loop to `stop_reason: "wall_clock_budget_reached"`, `iterations: 0`, `wall_clock_seconds: 60.0007` in a 60.46 s file run. **Fix:** `:465` remembers `proposals_before = self.state.proposal_attempts`; `:507-515` reclassifies a proposal-kind failure that charged no proposal as `harness`, so the breaker bounds it. Chosen over charging `proposal_attempts` because a replication is not a proposal (the ledger would lie) and `max_proposals` is 100 in the real config — 100 full-speed retries against a corrupt directory. It is also the more faithful reading of the brief's own table, which files "corrupt run dir" under harness; a truncated `manifest.json` is one that happens to surface as `JSONDecodeError` rather than `OSError`. **Invariant now:** every `continue` out of the handler advances a monotonic bounded counter — `proposal_attempts` (bounded by `max_proposals`) or `consecutive_harness_errors` (bounded by the breaker) — and the two cannot cancel, because the only branch that resets the breaker is the one that just advanced `proposal_attempts`.
- **Important 2 — `LLMError` subclasses classified as `harness`, inverting the brief's table.** `RoleOutputInvalid` and `IncompleteResponse` are not `ValueError`, so the original `_error_kind` sent them to `harness`. The brief assigns those raise sites (`roles.py:111/175/207`, `llm.py:276`) to **proposal**, so the day C converts them, malformed model output would stop being re-prompted and start tripping the breaker after three strikes — the precise inversion of C4's intent, failing silently. **Fix:** `LLMError` added to the proposal `isinstance` tuple, strictly after the budget check (`TokenBudgetExceeded` is itself an `LLMError`); bare `RuntimeError` deliberately **not** widened, so `llm.py:198,202,310` stay harness. This also explains the reviewer's M1: the brief's step-1 import of `LLMError` was never unused — it was the missing classification arm. Deliberate, coordinator-directed departure from the brief's verbatim `_error_kind` body.
- **Minor M2 — a test that could not fail.** `test_keyboard_interrupt_is_not_a_catchable_loop_error` only asserted `issubclass(KeyboardInterrupt, Exception)` is False, a fact about Python; it would have passed if `run()` caught `BaseException`. Rewritten to raise `KeyboardInterrupt` from a role call and assert it propagates out of `run()` with no `stop_reason`, no `error.json` and **no `summary.json`**. Verified it can now fail: temporarily changing `:505` to `except BaseException` made it FAIL, then reverted (`grep -n 'except BaseException'` → no hits, full suite re-run green after the revert).
